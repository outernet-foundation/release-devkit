# github-actions-toolkit

## What this is

The platform binding for outernet-foundation repos: everything that knows GitHub Actions exists. Renamed from `release-devkit` (the GitHub repo is renamed; redirects cover old URLs, and `lint-workflows` enforces the canonical spelling so a redirect can never mask a missed rename). It holds the reusable workflows every consumer composes (`preflight`, `mirror`, `merge-gate`, `build-unity`, `compile-check-unity`, `build-docker`, `update-pr-draft-release`), the release composite action, the delivery verbs (release orchestration, per-package version tags, path-diff change detection, ephemeral version patching, OIDC trusted publishing), the matrix helper (fanout envelope plus per-leg base-version stamping), and runner provisioning (absorbed from ci-devkit's `setup` with the vendored `third-party/` scripts). It must stay a project dependency of nothing — `bashrun` and `build-artifact-registry` are its runtime deps, so a project-level edge in any tool repo is a resolver cycle. Consumers reference it only through `uses:` at a full commit SHA; the code resolves from the consumer-side installs the reusables make.

Two names survive the repo rename deliberately, because they are fleet-facing and the migration does not move them: the Python package/distribution stays `release-devkit`/`release_devkit`, and the consumer-owned root config file stays `release-devkit.yaml`. Renaming either is a fleet-wide breaking change that the rearchitecture plan does not authorize.

The consumer owns everything declarative — package and app identities, paths, registry mappings, the builds shelf each app's release assets pull from — in a root `release-devkit.yaml`; every command reads it. Per-repo copies of this machinery are refused, as are per-ecosystem splits — the seam is internal: one `Registry` adapter per registry over the shared tags/diff/versioning core. Registry primitives (ORAS push/pull, the builds shelf, `setup_oras`, `registry_auth`) live in [`build-artifact-registry`](https://github.com/outernet-foundation/build-artifact-registry), a PyPI dependency; this repo owns no ORAS code.

## Installation and invocation

Consumers never clone this repo themselves. A consumer workflow references a reusable (`uses: outernet-foundation/github-actions-toolkit/.github/workflows/<file>.yml@<full-sha>`) or the release composite (`uses: outernet-foundation/github-actions-toolkit/.github/actions/release@<full-sha>` with `stable: true` or `false`); the `@sha` is the whole version control. Third-party action SHAs are pinned once, inside this repo's files — consumers pin nothing but this repo.

The install trio lives in three composite actions referenced via the `$/` self-repository syntax (`uses: $/.github/actions/toolkit-checkout`, `consumer-checkout`, `setup-uv`) — `$` resolves to this repository at the commit the caller pinned, so the composites are single-copy across every reusable and can never drift from the pin. Where a job runs binding verbs, `toolkit-checkout` comes first: `actions/checkout` at `job.workflow_repository`/`job.workflow_sha` — exactly the SHA the caller spelled — into `${{ runner.temp }}/github-actions-toolkit`, never the workspace, a nested clone would be scanned by the consumer's own lint/deptry; the contexts are referenced raw, no emptiness guard — hosted runners are current, and the self-hosted unity legs never call `toolkit-checkout` (they run no binding verbs). Then `consumer-checkout` with values only: `ref` (required — `github.event.pull_request.head.sha` where PR-gated, the `|| github.sha` fallback only where not) plus checkout's own `fetch-depth`/`fetch-tags` inputs forwarded raw (plain is the composite's defaults `1`/`false`; full is `0`/`true`; merge-gate's tags-less full clone passes `0` and omits `fetch-tags`). Composite inputs are typed (`type: number`/`type: boolean`) — actionlint never parses these files (it cannot resolve `$/`), so the old untyped-string constraint is void. Then `setup-uv` (`save-cache` input — preflight is the only saver). Binding verbs then run as `uv run --project "${{ runner.temp }}/github-actions-toolkit" --locked --no-dev <verb>` with cwd = the consumer root (`--project`, not `--directory` — `--directory` would chdir into the clone and break relative config resolution). The release composites self-install the same way off `${{ github.action_path }}/../..` — the runner's action archive download IS the install, no clone step.

Domain verbs (unity-devkit's `build-unity`/matrix verbs, docker-devkit's `build`/`mirror`/`docker-build-matrix`, python-devkit's `preflight-python`) are different: they are dev-group dependencies of the consumer, so they run `uv run --locked <verb>` against the consumer's synced workspace — the consumer's `uv.lock` is their version surface. `--locked` is universal law across both buses: a consumer lock out of date with its pyproject fails loudly at the first `uv run`, instead of uv re-resolving ephemerally on the runner — the committed lock is the certified version surface, never a suggestion. Structure is pinned by the `@sha` on the `uses:` ref; code by the consumer's lock.

The invocation grammar is env-indirection, and it is standing law inside every devkit-owned file: attacker-controllable expressions a `run:` step consumes (matrix values composed from the PR head tree, `needs.*.outputs.*`, workflow inputs) ride the step `env` block with the run line referencing the variable — bash parses the literal script before parameter expansion, so tainted text arrives only as word content, never as operators (zizmor's template-injection remediation). Known-immutable contexts may interpolate directly: `github.event.pull_request.head.sha`, `github.event.pull_request.number`, `github.sha`, `github.repository`; runner-controlled constants (`runner.temp`, `github.action_path`) likewise. Secrets (`GITHUB_TOKEN`, `UNITY_*`) ride step or job env, never run lines. GitHub-provided facts come from ambient runner env (`GITHUB_REPOSITORY`, `GITHUB_ACTOR`, `GITHUB_WORKSPACE`, `GITHUB_REF`), never as flags; `--config` is the local-run escape hatch.

The domain matrix verbs emit bare leg candidate lists on stdout; the binding pipes them through `matrix`, which composes the final fanout. Legs carry only per-leg-varying facts: each leg carrying a `project` key is resolved to its owning app (`apps.{name}.builds[].project` matched against the leg's `project`) and stamped with `version` (the bare `{next_version}` base — the same `next_version`/tag math the release verb uses; the domain devkits stay version-blind); legs without a `project` key (docker) and legs whose project no app owns pass untouched — unversioned builds are a supported mode — and compile-check legs carry the stamp inertly. `matrix` emits exactly one thing: the `{"include": …}` envelope as a `matrix=` line to `$GITHUB_OUTPUT`, guarding the empty-leg case loudly (an empty fanout fails in the getter, never at `fromJson` render time). Run-wide facts never ride the matrix and never enter the verb — a matrix include entry carrying a constant across all legs lies about cardinality: the unity license cache key is derived once per run by the getter calling the domain verb `unity-license-tag` (the daily UTC `v-` tag; grammar stays domain-owned), and `commit-count` is the repo-wide `git rev-list --count HEAD` derived by the getter's own count step. The fanout threads base and ordinal to the build verb as separate facts (`--version`, `--commit-count`) — no YAML composes anything. The verb renders the pair: `bundleVersion = {version}+{commit-count}` and `AndroidBundleVersionCode = commit-count` from one input pair, so the string and the integer cannot disagree. Rendering is not deriving — the binding derives both facts, the domain renders both fields.

## Consumption model (no publication)

Nothing is ever published from this repo — no PyPI wheel/sdist, no Release assets, no version tags. The commit history is the changelog; consumers pin by full commit SHA, and "what changed since our pin" is `git log <old>..<new>`. The committed `pyproject.toml` version is permanently the `0.0.0.dev0` sentinel. Bumping a consumer means changing the SHA in its `uses:` refs — all of them, to one SHA, enforced by the lint. The pinned SHA must exist on the remote before consumer CI runs, so this repo's branch is always pushed first.

Its own `integrate.yml` is one self-called `preflight` job (`uses: $/.github/workflows/preflight.yml` — the self-repository ref resolves at the caller's commit, no SHA, no self-pin). The repo's `scripts/preflight.py` runs the python battery plus the self-certification: a dynamic clone of this repo at the workspace HEAD into `$RUNNER_TEMP/github-actions-toolkit-self-test` (hand-spelled clone — `uses:` refs cannot carry context expressions, and the head is the SHA that would land, not `job.workflow_sha`'s merge ref), then the canonical `validate-release-plan` and `merge-gate --dry-run` run steps with cwd = this checkout, the consumer geometry exactly — the dry-run certifies the full landing machinery side-effect-free at the exact SHA that would land. Its own `merge-gate.yml` is the hybrid: it carries both the `pull_request: [labeled]` trigger (so this repo fires it directly) and `workflow_call` (so consumers call it remotely); one file serves both roles because a workflow cannot `uses:` itself.

## Commands

One console script per verb — script names and flags are public API (stable-CLI-API doctrine: the YAML surface every consumer writes names them).

| Command | Role |
|---|---|

The PR number parses from `GITHUB_REF`, so the job's `if: github.event.pull_request` gate is load-bearing. Every pr run stages every app — no unchanged-skip. |
| `validate-release-plan` | Run the shared plan core (`load_config` → `resolve_edges` → `compute_plan` → app-version math). No flags, no env, no writes, no output. Runs as preflight's second step, after lint. |
| `lint-workflows` | Four layers, in one pass over the found files (`.github/workflows/*.yml` plus every `.github/actions/**/action.yml`): **actionlint** and **zizmor** (both fetched as pinned, sha256-verified release binaries by the verb itself — zizmor's expected hashes are constants in this repo; offline persona, plain format, config committed beside the runner, audit input the repo root so composite actions are covered); actionlint runs with four `-ignore` bridge flags — two for `job.workflow_*` (rhysd/actionlint#696/#707; dormant since the contexts moved inside `toolkit-checkout`, kept for any future raw spelling) and two for the `$/` spelling (rhysd/actionlint#732; anchored on `$/` so `./`-ref and remote-format errors stay live) — riding until the ACTIONLINT_VERSION pin moves past the fixes; **the SHA law** — every `uses:` ref to this repository (workflow or action) is a full 40-hex SHA, all such refs in one repo carry the same SHA, the stale `release-devkit` spelling is a finding, and within-file YAML anchors (scalars and whole nodes alike) are sanctioned — YAML resolves them before the lint sees values; **the concurrency contracts** — `release.yml`'s group is `release-${{ github.ref }}` with no cancel (the delivery mutex), `merge-gate.yml`'s wake is `pull_request: [labeled]` to dev with no `workflow_run` and group `merge-gate-${{ github.event.pull_request.number }}` with no cancel. Found-file model: filename-keyed contracts for `release.yml`/`merge-gate.yml`; every other found file gets the SHA law only; a missing file means no contract applies. | `merge-gate` | The bors-model lander (see Landing changes). Flags: `--head-sha <sha>` — an event-payload fact with no ambient representation — and `--dry-run`, which exercises the whole machinery with zero side effects: precondition failures print as informational while machinery failures still fail loudly. |

## The workflow contract

The binding owns workflow MECHANICS; the consumer owns triggers, concurrency, permissions, the job graph, and secret forwarding. What follows is the law for the consumer-side residue (formatting retained, not reformed: blank lines between jobs and top-level keys, permissions and secrets as block maps, job key order `needs`, `permissions`, `uses`, `with`, `secrets`). No devkit-owned file carries YAML anchors (GitHub resolves anchors server-side and aliases cannot cross files; the trio's whole-step anchors died with the `$/` composites). Merge keys (`<<:`) are forbidden — GitHub's anchor support does not implement them (silently rejected, or worse, a bogus key in loose-key maps) — should repetition ever warrant anchors again.

Composites are leaves, and the layering is law: a composite input may carry values (a ref, a key, a boolean forwarded raw to a typed action input), never select structure — a composite needing two shapes becomes two composites and the caller spells the choice as a reference; `if:` conditionals are legitimate only on typed `workflow_call` inputs in workflow YAML (build-docker's `free_disk_space` gating the free-disk-space verb step is the shape); and no bash guard validates a spelling — a value that must not be silently wrong fails in its own consumer. Two platform walls enforce the shape. The `secrets` context is withheld from composite actions entirely — a parse failure (`Unrecognized named-value: 'secrets'`), not an empty string (github/docs#12705) — and is unavailable in `if:` conditions even in workflows, so a secret crosses only as a workflow-context expression. And `./` local `uses:` inside a composite resolves against the consumer's workspace, not the action's own checkout (actions/runner#1348), so a composite cannot reference its siblings via `./` — the `$/` self-repository reference is the fix and is in use for the install trio; the release composites nonetheless stay self-contained (their sibling-prelude dedup via `$/` is possible but not done, the duplicated prelude the accepted price).

- `integrate.yml` composes `uses:` calls: `mirror-images` (where images exist) is the single first root — provisioning precedes consumption, and its long-term destiny is hermeticity enforcement — then `preflight` (needs mirror), then the build legs (needs preflight), then `update-pr-draft-release` (needs the terminal build legs). A calling job accepts only `needs`, `if`, `permissions`, `with`, `secrets`, `strategy`, `concurrency`, `name` — never `steps` (that is what "use the reusable" means).
- `merge-gate.yml` is triggers + concurrency + permissions + one `uses:` call to this repo's `merge-gate.yml`, forwarding `secrets: {merge-bot-private-key: ${{ secrets.MERGE_BOT_APP_PRIVATE_KEY }}}` — secrets are never ambient across the call boundary; every hop forwards explicitly. The `vars.MERGE_BOT_APP_ID` var is read from the caller's vars (vars are visible in called workflows; secrets are not). The `ready-to-merge` label gate lives inside the reusable.
- `release.yml` stays ONE file for both channels: npm allows one trusted publisher per package, bound to a single workflow filename — a split would leave one channel unpublishable — and nuget.org binds owner/repo + workflow filename the same way, so `release.yml` must never be renamed. Its concurrency (`release-${{ github.ref }}`, NO cancel) is a queue and the policy: the `main` group is the release mutex, and the serialization makes the `dev-builds` read-modify-write append safe. Delivery jobs are one `uses:` of the release composite each, the channel spelled as the typed `stable` boolean (`true` for the stable job, omitted/false for dev) — the composite runs inline in the caller's job, so `job_workflow_ref` keeps naming the consumer's `release.yml` (warehouse#11096 blocks reusable-workflow publishers, not composites). The composite absorbs the checkout/no-ref/tag-fetch law (credentials persist for the tag push only on stable, via `persist-credentials: ${{ inputs.stable }}` — a boolean forwarded raw to checkout's typed input), setup-uv, the NuGet login, and the verb invocation (`RELEASE_CHANNEL: ${{ inputs.stable && 'stable' || 'dev' }}` riding step env, the run line referencing the variable). NuGet routing is the presence of the repo secret: the consumer maps `NUGET_USER` once in workflow-level env (`env: {NUGET_USER: ${{ secrets.NUGET_USER }}}` — one line serves both delivery jobs, the only sanctioned secret crossing into composite-land), the composite gates the login on `env.NUGET_USER != ''` and feeds the minted `NUGET_API_KEY` to the verb env. `NUGET_USER` is a per-repo secret, never org-level — org secrets are visible to every repo and would switch the login on fleet-wide.
- `workflow_run` is banned outright — zizmor's dangerous-triggers audit fires on it and no relaxation remains. `merge-gate` wakes only on the `ready-to-merge` label; the human is the green-and-rebased detector — the label is a verb ("attempt the merge now"), not standing intent.
- Jobs never `needs` across the file boundary — verification certifies on PRs, delivery runs on the landing push.
- Job `permissions:` are consumer-owned: mirror/build legs carry `contents: read, packages: write`; `update-pr-draft-release` carries `contents: read, packages: read` (shelf pulls); delivery jobs carry `contents: write, id-token: write` (trusted publishing) plus `packages: read` (prerelease shelf pulls) or `packages: write` (stable, where apps pull the shelf); the merge-gate call carries only `contents: read` — every write path rides the minted App token.
- The preflight script contract: a required Python script at the repo-root path `scripts/preflight.py`, invoked by the harness as `uv run --locked scripts/preflight.py` (no shebang, no executable bit), missing file a loud red — never a skip. The harness (this repo's `preflight.yml`) provides checkout at the PR head (full fetch), uv, docker on the runner, cwd = the repo root, and `GITHUB_TOKEN` in the step env; exit code is the whole interface. Per-consumer variance (e.g. `packages: read` for a preflight that pulls mirrored images) rides the calling job's permissions.
- Unity build legs: `runs-on: [self-hosted, unity]`, `container: ${{ matrix.editor-image }}`, a wipe-workspace first step (the self-hosted runners reuse the workspace), license threading via named `unity-email`/`unity-password`/`unity-serial` call-site secrets, and registry auth as `REGISTRY`/`REGISTRY_TOKEN`/`REGISTRY_USERNAME` step env (the `CI_` prefix is dead — the docker contract always spelled it this way). The leg schema (which keys a domain verb emits: `project`, `platform`, `editor-image`) is named contract with the domain devkits — renaming a key breaks this repo's fanout YAML; `version` is binding-injected by `matrix`, never domain-emitted. Run-wide facts reach the fanout as getter job outputs, each derived by its own single-output step — the license cache key (the getter calls `unity-license-tag` once; the domain verb flag that consumes it is `--license-cache-key`, named for what it is: the ORAS tag the license cache restores under, not a license) and `commit-count` (a plain `git rev-list --count HEAD` count step) — never as leg keys. The leg's step env carries every fact grouped by source — the leg's matrix facts (project, platform, version), the event fact (pr-number), the run-wide getter outputs (commit-count, license cache key), the unity secrets, the registry trio (registry, registry token, registry username) last — and the run line's switches follow that same order with the secrets elided (`--project`, `--platform`, `--version`, `--pr-number`, `--commit-count`, `--license-cache-key`, `--registry`): one source order everywhere. `build-unity` takes no mode switch — shelving (the build-output push plus the CI cache bundle) is implied by the supplied registry env, which the binding always supplies; absent registry env is the local build. The build verb composes `bundleVersion = {version}+{commit-count}` and stamps `AndroidBundleVersionCode = commit-count` from that one input pair — rendering, not deriving, so the string and the integer cannot disagree. The getters are named for their role (`plan-unity-builds`, `plan-unity-compile-checks`, `plan-docker-builds`), not for the transport format they emit.
- Docker build legs: matrix values env-indirected in `run:` lines; QEMU arm64 + buildx setup live inside `build-docker.yml`; `free_disk_space` is a reusable input, not a domain config key. The domain verb runs `build --push` with explicit parameters — registry, actor, and token supplied by the binding via step env (`REGISTRY`, `REGISTRY_TOKEN`, `REGISTRY_USERNAME`), never ambient `GITHUB_*` reads in domain code.
- Comments in devkit-owned files are minimal and end without a period; step `name:` survives only when it says something the command does not.

## Landing changes (the bors model)

`dev` is evergreen: nothing lands on it that was not certified green at the exact SHA that lands. Push a branch, open a PR to `dev`, let `integrate.yml` certify the head, then — once green AND rebased onto `dev` — apply the `ready-to-merge` label. The label is a verb, not standing intent: "attempt the merge now". A poke before green or before rebase fails loudly (pending checks are a loud refusal telling you to re-apply the label once green, never a silent stall); after a failure, a rebase, or a further push, re-poke by removing and re-applying the label. The label event is the sole wake; the verb owns all policy on every wake: label present, state OPEN, checkout-is-head, all-green, rebased-onto-dev (the all-green battery excludes the merge-gate check by name). It merges the PR head into `dev` with `--no-ff`, deletes the head branch, deletes the `pr-{N}` draft release, and the landing push fires `release.yml`. The merge bot holds the `evergreen-dev` ruleset's Integration bypass; with the ruleset active it is the only door. **Never label a PR in a repo without a live verification job** — the all-green assert is vacuously true on zero checks.

## The CI-commit-free invariants

CI and release workflows must not create non-merge commits on any branch — the merge-bot's `--no-ff` merge commit on `dev` is the only commit CI creates, and `dev` → `main` merges are always true fast-forwards.

- **Version tracking**: per-package git tags (`{name}-v{semver}`, e.g. `placeframe-api-client-v0.1.8`), never committed state files.
- **Change detection**: `git diff --quiet <last-tag> HEAD -- <path>`, never content hashing. No cascade: an unchanged dependent is an immutable, coherent pairing — UPM/npm treat declared dependency values as minimums, so a newer sibling always satisfies.
- **Version scheme**: major.minor is config data (the required `major_minor` on every package and app entry), patch is tag data: the highest stable tag within the declared line plus one patch, or `.0` when the line has no tags. A declared line below any existing tagged version fails loudly (never compute downward). Per-package numbers are independent within one release event — no lockstep.
- **Manifest version sentinels**: Unity `package.json` versions are permanently `0.0.0+local` in the repo; Python `pyproject.toml` versions permanently `0.0.0.dev0` — patched ephemerally at publish and restored immediately, never committed. The sdist/wheel carries the real version; the committed file never does.

## The dependency-edge law

Same-release-unit dependency edges are **inferred from manifests**, not authored in config: each package's manifest dependencies (package.json `dependencies` for npm, `[project].dependencies` for pypi, csproj `PackageReference` for nuget) are intersected with the config's registry identities; a match is an edge, everything else is an external dependency that ships verbatim. Edges drive topological plan ordering — dependencies-first, load-bearing for nuget, where `dotnet pack` restores the sibling from the registry — and validation only, never version selection.

Same-unit dependencies are authored as the sentinel `0.0.0+local` — one string that is valid semver (build metadata), PEP 440 (local version), and NuGet. The concrete version exists only in the published artifact, injected at publish from the event's plan: the sibling's new version if it co-publishes, its current tag if unchanged (HEAD is then byte-identical to that release), a loud error if it never published. The dev channel injects a co-publishing sibling's dev spelling (keyed on the same run count) and an unchanged sibling's current stable tag. Cross-unit and ecosystem dependencies are authored exact and shipped verbatim — adoption is a human commit.

Plan-time validations, all atomic before any registry call, all caught by `validate-release-plan`: a sentinel on a non-config identity; a real version where a config identity expects the sentinel (hard flip — staleness cannot ship); a sibling that has never published; cyclic edges.

### Reference regimes (how same-unit dependencies are wired on disk)

| Regime | Local | Publish |
|---|---|---|
| Unity sibling, same project | asmdef assembly-name references | package.json sentinel, ephemeral patch |
| Same repo, outside the consuming project | `file:` path in the project's Packages/manifest.json + asmdef name | package.json sentinel, ephemeral patch |
| Cross-repo (lbe-toolkit → placeframe) | exact registry pin in the consumer's project manifest | the same adopted pin, verbatim |
| Ecosystem deps (UniTask, org.nuget.*) | authored exact | verbatim |
| nuget sibling | ProjectReference (version-free) | `PackageReference Version="$(Prop)"` with the property defaulting to `0.0.0+local`; injected via `-p:<Prop>=<version>` beside `-p:Version` |
| pypi sibling | `[tool.uv.sources]` workspace override | `name==0.0.0+local`, specifier patched ephemerally |

## Dev channel

The dev channel (`release --channel dev`) publishes immutable prereleases of every path-diff-changed package and appends a per-SHA snapshot section to the `dev-builds` draft: every package (this run's dev version + registry link when changed, latest stable tag otherwise), every app (a row with a fresh count-suffixed asset link), and every built image (the full digest manifest). Sections are snapshots, not changelogs — every merge writes one, re-listing all artifacts at that SHA; there is no app-level change detection in the dev channel, so each run re-pulls and re-uploads every app's shelf build at that SHA — the churn is the accepted cost of not trusting change detection. It creates no git tags, bumps no app versions, opens no release (the dev draft is a `draft: true` GitHub Release, not a published one). Versions are keyed on the commit count at the certified head (`git rev-list --count {sha}`, computed once per run and threaded to packages and asset names — the same ordinal the build verb composes into the app binaries' version strings; counting HEAD would run one ahead, because the merge commit adds one) and spelled per registry — `{base}.dev{count}` on PyPI, `{base}-dev.{count}` on nuget and npm; no hex SHA can ride a PyPI dev version (PEP 440's `.dev` segment must be numeric), while the count re-derives the same version idempotently on re-runs. The base is the next version derived from the declared `major_minor` and the tags, so dev versions share one base until the stable flow tags it. npm prereleases ride the single inert `dev` dist-tag so `latest` never moves.

## Draft release surfaces

Three surfaces expose CI-built APKs and built images, all mirroring the ghcr builds shelf (which stays canonical — the unity build leg pushes player binaries and the docker build leg pushes the digest manifest there, all `sha-{full}`-keyed; `release` on every channel staples from there):

- **PR draft** (`pr-{N}` tag): one draft release per open PR of every publishing consumer; each run appends a count-suffixed asset per app and lists the run's built images. `release --channel pr` writes it from `update-pr-draft-release.yml`; `merge-gate` deletes it after the merge. Abandoned PRs' drafts linger — hidden, a minor accepted leak.
- **Dev draft** (`dev-builds` tag): one rolling draft accumulating every merged PR's section since the last promotion to main; `release --channel stable` resets it after cutting the CalVer release. The tag is `dev-builds`, not `dev` (which collides with the `dev` branch). Sections are keyed by `<a id="sha-{short}"></a>` HTML anchors.
- **Main release** (CalVer `YYYY.MM.N`): `release --channel stable` cuts one asset per platform — the promoted build — and its body lists the same three artifact tables the draft sections use, rendered by the same spine so the surfaces cannot drift.

Asset naming: drafts use `{stem}-{count}.{ext}`; the main CalVer release keeps the bare configured `file`. The SHA survives only as identity, never as a version: the `sha-{full}` builds-shelf keying and the sections' `sha-{short}` anchors.

## The Registry seam

One `Registry` adapter per registry (`publishing.py`: `NuGetRegistry`, `NpmRegistry`, `PyPIRegistry`), driven by the package loop in `publish_packages` (`verbs/release.py`), each `publish(path, base_version, resolved_dependencies, dev, commit_count) -> str` — the adapter resolves the channel spelling itself and returns the version it published; adapters also own their package-page grammar (`url(identity, version)`), so release-note links ask the same seam; the adapters derive the package's registry identity from the package's own manifest, so no identity is passed. A package's registry identity is config data, not code — every package declares exactly one `registry` and its `identity` there, a required pair validated against `KNOWN_REGISTRIES` at config load; each adapter packs from its own manifest type under the package path, so one package is one ecosystem.

All three are keyless from the consumer's secret store. PyPI authenticates via trusted publishing (OIDC): the consuming job needs `id-token: write` and the project a configured (or pending) publisher; idempotent re-publishing rides `uv publish --check-url`. npm authenticates the same way (`--provenance`, no token plumbing). nuget joins through the official `NuGet/login@v1` action (pinned by SHA inside the composite), which exchanges the job's OIDC token for a ~1h API key the composite feeds the adapter; `NUGET_USER` reaches it via the workflow-level env crossing (see the workflow contract — the secrets context never enters composite-land).

## Config

`config.PublishConfig` (pydantic, `extra="forbid"` on every model) validates the root `release-devkit.yaml`, loaded strictyaml-first (duplicate keys rejected, all scalars preserved as strings — pydantic coerces per-field). Hard flips, no accept-both: an unmigrated or unknown key fails loudly at load. All keys optional — an empty document loads as the empty config; `packages` and `apps` map by name, which doubles as the git-tag prefix.

The builds shelf address is derived, never configured: `ghcr.io/{repository}/builds` from the ambient `GITHUB_REPOSITORY`. Keying law: every shelf artifact is tagged `sha-{full}` where the SHA is the certified PR-head SHA integrate built at. Apps declare their artifacts directly: `builds` is a required, non-empty list of entries carrying `project` and `platform` — the push side's exact spelling, so the pull side cannot drift from whatever pushed the shelf — and `file`, the release-facing filename. One shelf layer holds exactly one file, the build's single player binary (build reports push to their own `{project}-{platform}-report` reference); the push side guarantees it. A root `built_images: true` declares the repo's CI builds images and shelves the digest manifest; declared, a missing manifest at the certified SHA is a loud failure.

The config-file law org-wide (home: this file; siblings reference it, they don't duplicate it): config lives beside the unit whose facts it carries. A tool whose subject is the Python project configures from pyproject `[tool.<devkit>.*]` tables; every other devkit uses one root `<devkit>.yaml` per repo. python-devkit is the one pyproject-table devkit; unity-devkit the one JSON exception (read by C# inside Unity); this repo / openapi-client-codegen / docker-devkit are root `.yaml`.
