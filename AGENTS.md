# release-devkit

## What this is

The publication machinery for outernet-foundation repos: the publish pipeline, per-package version tags and path-diff change detection, ephemeral version patching, manifest-inferred dependency edges, and release orchestration. A standalone repo, **published nowhere and versioned not at all**: consumers install it as a git clone at a pinned commit SHA via a per-consumer setup action. It must stay a project dependency of nothing — bashrun and ci-devkit are its runtime deps, so a project-level edge in any tool repo is a resolver cycle. The clone is the seal: the whole dependency closure resolves from the committed `uv.lock`; execution forms that resolve around it (`uv run --with`, `uvx --from`, unlocked sync, bare `uv pip install`) are forbidden.

The consumer owns everything declarative — package and app identities, paths, registry mappings, the builds shelf each app's release assets pull from — in a root `release-devkit.yaml`; every command reads it. Per-repo copies of this machinery are refused, as are per-ecosystem splits — the seam is internal: one `Registry` adapter per registry over the shared tags/diff/versioning core.

The package is `release-devkit` (src-layout under `src/release_devkit/`; import `release_devkit`). Runtime deps: `bashrun` (all shell-outs), `ci-devkit` (`ci_step`, runner setup, `builds`), `pydantic`/`pydantic-settings`, `strictyaml`, `typer` — first-party deps exact-pinned (`bashrun==`, `ci-devkit==`) so any fresh resolve is deterministic.

## Installation and invocation

Each job needing release logic runs `uses: ./.github/actions/setup-release-devkit` — a per-consumer composite action whose only reason to exist is being the single place the pinned SHA appears (a full 40-hex commit SHA, never a branch or tag — a movable ref reintroduces version float), so no number of workflow files can drift apart: one `bash` step carrying `RELEASE_DEVKIT_COMMIT` in step env above a two-line tokenless clone of this repo into `$RUNNER_TEMP/release-devkit` and checkout of the pin. `$RUNNER_TEMP` is the sanctioned install location — it keeps the devkit out of the consumer tree, where `deptry .` and `ruff check .` would scan it as the consumer's own code. Local `uses: ./...` resolves only inside `$GITHUB_WORKSPACE`, so the wrapper must live in the consumer repo; the remote `uses: owner/repo@ref` form would re-scatter the SHA per verb step.

Verbs are plain run steps in the caller's workflow: `uv run --project "$RUNNER_TEMP/release-devkit" --locked --no-dev <verb>`, cwd = the consumer root (`--project`, not `--directory` — `--directory` would chdir the verb into the devkit clone, breaking relative `release-devkit.yaml` resolution and pointing `git tag` at the devkit repo). The wrapper does not provision uv: every uv-consuming job spells `astral-sh/setup-uv@v7` itself. Canonical order: checkout → setup-uv → wrapper → (token mint) → verb. The invocation grammar is `lint-workflows`-enforced: GitHub-provided facts come from ambient runner env (`GITHUB_REPOSITORY`, `GITHUB_ACTOR`, `GITHUB_WORKSPACE`, `GITHUB_REF`), never as flags and never in the step env block; secrets (`GITHUB_TOKEN`, `NUGET_API_KEY`) ride the step env block. There is no `CI_REGISTRY_*` anywhere in this tool's contract — `GITHUB_ACTOR` flows from ambient env to ci-devkit's explicit-parameter door. `--config` is the local-run escape hatch.

Verbs must stay inline run steps: an inline `run:` executes in the caller's job, so `job_workflow_ref` resolves to the **caller's** workflow file — the OIDC trusted-publishing identity PyPI hard-requires (warehouse#11096 blocks reusable-workflow publishers) and npm binds. Reusable workflows remain the one forbidden conversion for the delivery jobs.

## Consumption model (no publication)

Nothing is ever published from this repo — no PyPI wheel/sdist, no Release assets, no `release-devkit-v*` tags. The commit history is the changelog; consumers pin by full commit SHA, and "what changed since our pin" is `git log <old>..<new>`. Its own `integrate.yml` is preflight-only (PR/dispatch gated, nothing on `main`; this repo has no `release.yml`): `preflight-python` plus a self-test that installs this repo at the PR-head SHA into `$RUNNER_TEMP/release-devkit` (a hand-spelled clone, not the wrapper — `uses:` refs cannot carry context expressions) and runs the canonical `validate-release-plan` run step with cwd = this checkout, the consumer geometry exactly. For that dynamic-SHA reason the repo's own `integrate.yml` carries no `lint-workflows` job — it cannot lint its own contract. The committed `pyproject.toml` version is permanently the `0.0.0.dev0` sentinel. Bumping a consumer means changing the SHA in its wrapper; the pinned SHA must exist on the remote before consumer CI runs, so this repo's branch is always pushed first.

## Commands

One console script per verb — script names and flags are the public API. Workflow jobs run them via the canonical invocation above; humans run `uv run <verb>` from a checkout. Config defaults to `release-devkit.yaml` where optional.

| Command | Role |
|---|---|
| `get-app-version` | Print the version a CI build of an app should stamp: `version={next_version}+{short}` (`short` = first 12 chars of HEAD) and `version-code={count}` (`git rev-list --count HEAD -- {app.path}`, serving Android's monotonic `bundleVersionCode`), to `$GITHUB_OUTPUT` when set, stdout otherwise. The same `next_version` `release` will tag, so the build-time stamp matches the eventual release tag — this tool owns version derivation, build tools own stamping. Flags: `--app <name>`. |
| `release` | Stable channel: compute the plan from version tags + path-diff, publish every changed package, bump and tag app versions, push per-package tags, cut the CalVer GitHub Release (inside the verb — no separate step), then reset the `dev-builds` draft so the next merge to dev starts a fresh pile. App versions bump unconditionally whenever any package publishes — a filtered run that skipped them would permanently lose the app-bump window (nothing later re-triggers it). |
| `prerelease` | Dev channel: publish immutable prereleases of every path-diff-changed package, then append a per-SHA snapshot section to the `dev-builds` draft (see Dev channel). Never creates git tags, never touches app versions. |
| `validate-release-plan` | Run the shared plan core (`load_config` → `resolve_edges` → `compute_plan` → app-version math) — the plan-time gate that catches every plan-time validation (sentinel misuse, never-published siblings, cyclic edges) before any registry call. No flags, no env, no writes, no output. |
| `lint-workflows` | The install-and-invocation gate: actionlint (pinned, checksum-verified) plus pure-Python signature validation of the consumer's workflows and wrapper. **The lint is the spec** for every canonical workflow spelling — checkout signatures, setup-uv forms, per-verb flags and env, ordering, merge-gate triggers, run-step folding. Copy an existing consumer's files; where prose and lint disagree, the lint wins. |
| `merge-gate` | The bors-model lander (see Landing changes). Flags: `--head-sha <sha>` — an event-payload fact with no ambient representation (`GITHUB_SHA` is the synthetic merge commit under `pull_request` and the branch tip under `workflow_run`). |
| `update-pr-draft-release` | Pull each app's build artifacts from the ghcr builds shelf at HEAD (the PR head — this verb runs in integrate.yml, where the checkout IS the PR head; the merge commit is not fetched and must not be resolved here) and upload them as `{stem}-{short}.{ext}` assets to a `pr-{N}` draft Release; `--clobber` makes re-runs replace same-named assets while new SHAs append. The PR number parses from `GITHUB_REF` (`refs/pull/{N}/merge`), so the job's `if: github.event.pull_request` gate is load-bearing. Every run stages every app with builds — there is no unchanged-skip; a config with no buildable apps still lists built images when `builds_registry` is set. |

No verb takes a SHA flag — the checkout is the commit identity: `release`/`prerelease` read HEAD (the pushed merge commit) and resolve the certified PR head from it; `get-app-version`/`update-pr-draft-release` run where HEAD already is the PR head. The two identity modes are the two named constructors in `context.py` (`merge_push_context` resolves `parents[1]`; `pr_head_context` takes HEAD as-is — update-pr-draft must use the latter), both returning the shared `VerbContext` that also carries settings, config, and the digest manifest.

## The workflow contract

Every publishing consumer runs three workflow files split by triggering event (non-publishing repos — the infra trio — run `integrate.yml` + `merge-gate.yml` only). The full byte-exact contract is lint-enforced; what follows is the law the lint cannot express or the rationale an agent would otherwise rediscover the hard way:

- `release.yml` stays ONE file for both channels: npm allows one trusted publisher per package, bound to a single workflow filename — a split would leave one channel unpublishable — and nuget.org's trusted publishing binds owner/repo + workflow filename the same way, so `release.yml` must never be renamed. Its concurrency (`release-${{ github.ref }}`, NO cancel) is a queue and the policy: the `main` group is the release mutex that must never drop a release mid-flight, queuing dev publishes gives every merge its prerelease set 1:1, and the serialization makes the `dev-builds` read-modify-write append safe.
- The `workflow_run` trigger in `merge-gate.yml` is a scoped carve-out of the org-wide ban — sanctioned ONLY as merge-gate's completion wake, still forbidden as a delivery bridge. It exists because no `pull_request` activity type fires at checks-green and `check_run`/`check_suite` never fire for Actions-created checks; the payload carries no PR number and no labels, which is why the verb-side label/state asserts are mandatory. The workflow_run receiver is read from the DEFAULT branch (`main`): the green wake is inert per repo until `merge-gate.yml` reaches `main` via that repo's next release, while the label wake works from `dev` immediately — harmless, the file is a thin shell (all policy rides the verb).
- Jobs never `needs` across the file boundary — verification certifies on PRs, delivery runs on the landing push; a push run re-verifying would be double-running. Inside `integrate.yml`, `lint-workflows`/`validate-release-plan`/`mirror-images` (where present) are the parallel roots; matrix getters keep `needs: [preflight, validate-release-plan]` so a broken `release-devkit.yaml` fails at minute 1 instead of after a 40-minute build that could never ship.
- Ref law, one sentence per file: Integrate checks out the PR head (`ref: ${{ github.event.pull_request.head.sha }}` — the certified tree is the landed tree byte-for-byte); Release checks out what was pushed (NO ref — a spelled branch name is a movable pointer that can race a queued delivery run's newer push and publish the wrong tree); merge-gate checks out the certified SHA (dual-payload `||` ref — workflow_run events carry no branch identity).
- The `get-app-version` step (`id: version`) writes `version`/`version-code` straight to `$GITHUB_OUTPUT`; the `validate-release-plan` job exports both as outputs matrix legs read (`needs.validate-release-plan.outputs.version` / `.version-code`).
- Job `permissions:` are consumer-owned, not lint-enforced: delivery jobs carry `contents: write` + `id-token: write` (trusted publishing), with `packages: read` on `prerelease`/`update-pr-draft-release` (shelf pulls) and `packages: write` on `release` where apps pull the shelf; `validate-release-plan` is `contents: read`; the merge-gate job carries only `contents: read` — every write path rides the minted App token, which must itself carry `Contents: write` (the ruleset's Integration bypass and the `pr-{N}` draft deletion both depend on it).
- The canonical mint step spells `app-id:` even though the action's current line deprecates it in favor of `client-id` — the pinned actionlint's bundled metadata predates that flip and rejects `client-id`; the spelling flips only when the actionlint pin bumps past the metadata change.
- Comments in the canonical files are minimal and end without a period, only where the established files show them (above `fetch-depth: 0` and the release job's `persist-credentials: true`); no comment on any `ref:`, `fetch-tags`, or `persist-credentials: false`. Step `name:` survives only when it says something the command does not; verb restatements die. Repeated steps within a file use whole-step YAML anchors, anchored at first use, no merge keys (`<<:`), no cross-file aliasing. A documented convention, not lint-enforced.
- Still never `pull_request: [main]`: promotion is a push (`git push origin <sha>:main`), so no PR to `main` exists to fire anything; `main`'s branch protection must require no status checks.

## Landing changes (the bors model)

`dev` is evergreen: nothing lands on it that was not certified green at the exact SHA that lands. Push a branch, open a PR to `dev`, let `integrate.yml` certify the head, then apply the `ready-to-merge` label (adjective, standing intent — "land this when green"; survives rebases and further pushes, never needs re-applying). Two wakes run `merge-gate` — the label event (consent) and Integrate's green completion (readiness); the verb owns all policy on every wake: label present, state OPEN, checkout-is-head, all-green, rebased-onto-dev. It merges the PR head into `dev` with `--no-ff` (semi-linear: the merge commit marks the merge point without changing the tree), deletes the head branch (guarding `dev`/`main`, tolerating already-deleted), deletes the `pr-{N}` draft release, and the landing push fires `release.yml`. The merge bot holds the `evergreen-dev` ruleset's Integration bypass (managed in infra-github-org); with the ruleset active it is the only door. **Never label a PR in a repo without a live verification job** — the all-green assert is vacuously true on zero checks, and a lint-less repo would merge uncertified.

## The CI-commit-free invariants

CI and release workflows must not create non-merge commits on any branch — the merge-bot's `--no-ff` merge commit on `dev` is the only commit CI creates, and `dev` → `main` merges are always true fast-forwards.

- **Version tracking**: per-package git tags (`{name}-v{semver}`, e.g. `placeframe-api-client-v0.1.8`), never committed state files.
- **Change detection**: `git diff --quiet <last-tag> HEAD -- <path>`, never content hashing. No cascade: an unchanged dependent is an immutable, coherent pairing — UPM/npm treat declared dependency values as minimums, so a newer sibling always satisfies.
- **Version scheme**: major.minor is config data (the required `major_minor` on every package and app entry), patch is tag data: the highest stable tag within the declared line plus one patch, or `.0` when the line has no tags. A declared line below any existing tagged version fails loudly (never compute downward). Per-package numbers are independent within one release event — no lockstep.
- **Manifest version sentinels**: Unity `package.json` versions are permanently `0.0.0+local` in the repo; Python `pyproject.toml` versions permanently `0.0.0.dev0` — patched ephemerally at publish and restored immediately, never committed. The sdist/wheel carries the real version; the committed file never does.

## The dependency-edge law

Same-release-unit dependency edges are **inferred from manifests**, not authored in config: each package's manifest dependencies (package.json `dependencies` for npm, `[project].dependencies` for pypi, csproj `PackageReference` for nuget) are intersected with the config's registry identities; a match is an edge, everything else is an external dependency that ships verbatim. Edges drive topological plan ordering — dependencies-first, load-bearing for nuget, where `dotnet pack` restores the sibling from the registry — and validation only, never version selection.

Same-unit dependencies are authored as the sentinel `0.0.0+local` — one string that is valid semver (build metadata), PEP 440 (local version), and NuGet. The concrete version exists only in the published artifact, injected at publish from the event's plan: the sibling's new version if it co-publishes, its current tag if unchanged (HEAD is then byte-identical to that release), a loud error if it never published. The dev channel injects a co-publishing sibling's `-dev.{short}` spelling and an unchanged sibling's current stable tag. Cross-unit and ecosystem dependencies are authored exact and shipped verbatim — adoption is a human commit.

Plan-time validations, all atomic before any registry call, all caught by `validate-release-plan`: a sentinel on a non-config identity; a real version where a config identity expects the sentinel (hard flip — staleness cannot ship); a sibling that has never published; cyclic edges.

### Reference regimes (how same-unit dependencies are wired on disk)

| Regime | Local | Publish |
|---|---|---|
| Unity sibling, same project | asmdef assembly-name references | package.json sentinel, ephemeral patch |
| Same repo, outside the consuming project | `file:` path in the project's Packages/manifest.json + asmdef name | package.json sentinel, ephemeral patch |
| Cross-repo (lbe-toolkit → placeframe) | exact registry pin in the consumer's project manifest | the same adopted pin, verbatim |
| Ecosystem deps (UniTask, org.nuget.*) | authored exact | verbatim |
| nuget sibling | ProjectReference (version-free) | `PackageReference Version="$(Prop)"` with the property defaulting to `0.0.0+local`; injected via `-p:<Prop>=<version>` beside `-p:Version` |
| pypi sibling | `[tool.uv.sources]` workspace override | `name==0.0.0+local`, specifier patched ephemerally |

## Dev channel

`prerelease` publishes immutable prereleases of every path-diff-changed package and appends a per-SHA snapshot section to the `dev-builds` draft: every package (this run's dev version + registry link when changed, latest stable tag otherwise), every app (a row in the section's app table with a fresh SHA-suffixed asset link), and every built image (the full digest manifest). Sections are snapshots, not changelogs — every merge writes one, re-listing all artifacts at that SHA; there is no app-level change detection anywhere in the dev channel, so each run re-pulls and re-uploads every app's shelf build at that SHA, stamp-only rebuilds included — the churn is the accepted cost of not trusting change detection. It creates no git tags, bumps no app versions, opens no release (the dev draft is a `draft: true` GitHub Release, not a published one). Versions are keyed by the certified SHA and spelled per registry — `{base}-dev.{short}` where semver allows it (nuget, npm), `{base}.dev{short}` on PyPI — because no single string is both valid semver and PEP 440. The base is the next version derived from the declared `major_minor` and the tags, so dev versions share one base until the stable flow tags it. npm prereleases ride the single inert `dev` dist-tag so `latest` never moves. The draft section's version listings are the consumption interface — consumers pin by hand, there is no discovery tooling.

## Draft release surfaces

Three surfaces expose CI-built APKs and built images, all mirroring the ghcr builds shelf (which stays canonical — `ci-build-unity` pushes `sha-{full}` tags there; `install`, `prerelease`, and `release` staple from there):

- **PR draft** (`pr-{N}` tag): one draft release per open PR; each run appends a SHA-suffixed asset per app and lists the run's built images — all builds visible, not just latest. `update-pr-draft-release` writes it in `integrate.yml`; `merge-gate` deletes it after the merge. Abandoned PRs (closed without merge) never trigger `merge-gate`, so their drafts linger — hidden (`draft: true`), a minor accepted leak.
- **Dev draft** (`dev-builds` tag): one rolling draft accumulating every merged PR's section since the last promotion to main. `prerelease` appends the per-SHA section; `release` resets the draft after cutting the CalVer release. The tag is `dev-builds`, not `dev` (which collides with the `dev` branch in the refs namespace). Sections are keyed by `<a id="sha-{short}"></a>` HTML anchors (release bodies get no auto heading anchors; inline anchors render and scroll).
- **Main release** (CalVer `YYYY.MM.N`): `release` cuts one asset per platform — the promoted build — and its body lists the same three artifact tables the draft sections use (packages with registry links, apps with versions and asset links, built images), rendered by the shared `render_*_table` helpers so the two surfaces cannot drift. The release is created the same way drafts are — ensure a draft release targeting the certified head (`--target`, never the default-branch tip gh would tag), upload assets with `--clobber`, then publish by editing `--draft=false` with the notes — so it becomes consumer-visible only once complete.

Asset naming: drafts use `{stem}-{short}.{ext}` where stem = the configured `name` without extension (or the source file's stem when `name` is unset); the main CalVer release keeps the bare configured `name`.

## The Registry seam

One `Registry` adapter per registry (`publishing.py`, beside `publish_packages` which drives them): `NuGetRegistry`, `NpmRegistry`, `PyPIRegistry`, each `publish(path, base_version, resolved_dependencies, dev, short_sha) -> str` — the adapter resolves the channel spelling itself (dev versions via its own `dev_version` grammar, co-publishing sibling dependencies dev-spelled, unchanged ones verbatim) and returns the version it published; the adapters derive the package's registry identity from the package's own manifest (csproj/package.json/pyproject), so no identity is passed; the dev flag's tag consumer is `NpmRegistry`, which rides the inert `dev` dist-tag so `latest` never moves. A registry's identity (nuget package id, npm name, PyPI distribution name) is config data, not code — the same package can publish to several registries at one version; config-declared registry names are validated against `KNOWN_REGISTRIES` at config load.

All three are keyless from the consumer's secret store. PyPI authenticates via trusted publishing (OIDC): the consuming workflow needs `id-token: write` and the project a configured (or pending) publisher; idempotent re-publishing rides `uv publish --check-url`. npm authenticates the same way (`--provenance`, no token plumbing). nuget joins through the official `NuGet/login@v1` action, which exchanges the job's OIDC token for a ~1h API key it exports as `NUGET_API_KEY` (the `NUGET_USER` org secret is a public profile name and routing parameter, not a credential); the adapter consumes that minted key.

## Config

`config.PublishConfig` (pydantic, `extra="forbid"` on every model) validates the root `release-devkit.yaml`, loaded strictyaml-first (duplicate keys rejected, all scalars preserved as strings — pydantic coerces per-field). Hard flips, no accept-both: an unmigrated or unknown key fails loudly at load. All keys optional — an empty document loads as the empty config; `packages` and `apps` may be omitted when empty. Both map by name, which doubles as the git-tag prefix; there is no `display_name`/`tag_prefix`, no `requires` field, and no config-level version check (the wrapper action's SHA pin is the only version control).

A repo-level `builds_registry` (e.g. `ghcr.io/{owner}/{repo}/builds`) is required when any app declares `builds`. An app's `builds` is a list of artifact entries carrying `project` and `platform` — the push side's exact spelling, composed through ci-devkit's `build_reference` so the pull side cannot drift from whatever pushed the shelf — plus optional `file` (which pulled layer becomes the asset when a build pushes several; APK builds also push `BuildReport.json`) and `name` (asset rename). Apps without `builds` release with no stapled assets.

The config-file law org-wide (home: this file; siblings reference it, they don't duplicate it): config lives beside the unit whose facts it carries. A tool whose subject is the Python project configures from pyproject `[tool.<devkit>.*]` tables (the black/ruff pattern); every other devkit uses one root `<devkit>.yaml` per repo. python-devkit is the one pyproject-table devkit; unity-devkit the one JSON exception (its config is read by C# inside Unity, which ships no YAML parser); release-devkit / openapi-client-codegen / docker-devkit are root `.yaml`.
