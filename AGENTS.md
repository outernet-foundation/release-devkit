# release-devkit

## What this is

The publication machinery for outernet-foundation repos: the publish pipeline, the per-package version tags and path-diff change detection, ephemeral version patching, manifest-inferred dependency edges, and release orchestration. A standalone repo (sibling of `unity-devkit` / `docker-devkit` / `bashrun`), **published nowhere and versioned not at all**: it is consumed exclusively as a git clone at a pinned commit SHA, installed by a per-consumer setup action. It must stay a project dependency of nothing (the reason is structural: every tool repo it publishes sits inside its own dependency graph — bashrun and ci-devkit are release-devkit's runtime deps — so a project-level release-devkit edge in those repos is a resolver cycle plus a root-version conflict against the committed version sentinel), and the clone is the seal: the whole dependency closure resolves from the clone's committed `uv.lock`, exactly like every other devkit consumption in the org — no run-time float, no published artifact to drift from its lock. That lock is non-negotiable in every execution context: whatever runs this package's code — the run steps, `uv run` from a checkout — installs strictly from the committed lock; execution forms that resolve around it (`uv run --with`, `uvx --from`, unlocked sync, bare `uv pip install`) are forbidden.

The consumer owns everything declarative: package and app identities, paths, registry mappings, and the builds shelf each app's release assets pull from live in a consumer-authored `release-devkit.yaml` at the repo root; every command here reads that file. Per-repo copies of this machinery are refused, as are per-ecosystem splits — the seam is internal: one `Registry` adapter per registry over the shared tags/diff/versioning core.

The package is `release-devkit` (src-layout under `src/release_devkit/`; import `release_devkit`). Runtime dependencies: `bashrun` (all shell-outs), `ci-devkit` (`ci_step`, runner setup, `builds` — release-asset pulls), `pydantic`/`pydantic-settings` (config + CI env), `strictyaml` (config loading), `typer` (CLIs) — all from PyPI, zero domain dependencies. First-party dependencies are exact-pinned (`bashrun==`, `ci-devkit==`) so any fresh resolve is deterministic; the committed lock is the consumption contract.

Each job needing release logic runs a step `uses: ./.github/actions/setup-release-devkit` — a per-consumer wrapper action that installs this repo as a tool on the machine: a single `bash` step carrying the pin in a step-level `RELEASE_DEVKIT_COMMIT` env var (a full 40-hex commit SHA — never a branch or tag, a movable ref reintroduces version float) above a two-line script, a tokenless `git clone` of the public repo into `$RUNNER_TEMP/release-devkit` then `git checkout "$RELEASE_DEVKIT_COMMIT"`. The wrapper's only reason to exist is being the single place the SHA appears, so no number of workflow files can drift apart; `lint-workflows` validates the wrapper's whole install contract (exactly one step, the env-carried pin, the canonical two-line clone), not just the pin. `$RUNNER_TEMP` is the sanctioned install location (setup-uv installs python/uv there; the runner itself clones remote actions outside the workspace) and it keeps the devkit out of the consumer tree — the previous in-workspace `.release-devkit` checkout polluted the consumer's own battery, because `deptry .` and `ruff check .` walk the repo root and scanned the devkit's code as the consumer's. Platform fact that forces the wrapper shape (verified, not assumed): local `uses: ./...` resolves only inside `$GITHUB_WORKSPACE`, so the install cannot itself be an action living in `RUNNER_TEMP`; the remote `uses: owner/repo@ref` form remains possible but re-scatters the SHA per verb step. Verbs are then plain run steps in the caller's workflow — `uv run --project "$RUNNER_TEMP/release-devkit" --locked --no-dev <verb>` — executed with cwd = the consumer root (`--project`, not `--directory`: `--directory` would chdir the verb into the devkit clone, breaking relative `release-devkit.yaml` resolution and pointing `git tag` at the devkit repo). The wrapper does not provision uv: every uv-consuming job spells `astral-sh/setup-uv@v7` itself, and the canonical preparation order is checkout → setup-uv → wrapper → (mint) → verb, lint-enforced up to the wrapper. The consumer spells the env the verbs need (`GITHUB_TOKEN`) in the step; `lint-workflows` validates the invocation spelling, the per-verb flag and env contracts, and the ordering rules. The consumer's job owns `permissions:` and its own checkout.

An inline `run:` step executes in the caller's job, so `job_workflow_ref` resolves to the **caller's** workflow file: the OIDC trusted-publishing identity is the caller's own, which is the property PyPI hard-requires (warehouse#11096 blocks reusable-workflow publishers) and npm binds (the caller's top-level workflow filename). Verbs as plain run steps are maximally inline — there is no longer even a composite-action boundary between the verb and the caller's workflow; reusable workflows remain the one forbidden conversion for the delivery jobs.

## Consumption model (no publication)

Nothing is ever published from this repo — no PyPI wheel/sdist, no Release assets, no `release-devkit-v*` tags. The commit history is the changelog, and consumers pin by full commit SHA; "what changed since our pin" is `git log <old>..<new>`. There is no versioning of the tool itself (the tags machinery serves consumers' own packages). Its own `integrate.yml` is `preflight`-only (PR/dispatch gated, nothing runs on `main`; this repo has no `release.yml` — validate-release-plan jobs exist only in publishing repos): `preflight-python` plus a self-test that installs this repo at the PR-head SHA into `$RUNNER_TEMP/release-devkit` and runs the canonical `validate-release-plan` run step with cwd = this checkout — the consumer geometry exactly. The install is a hand-spelled `git clone` + `git checkout` (not the wrapper) because the wrapper's SHA is validated as a 40-hex literal and `uses:` refs do not permit context expressions; for the same dynamic-SHA reason the self-test job is exempt from its own `lint-workflows` contract, which is why lint-workflows is never run against this repo's own workflows; the repo's own `integrate.yml` accordingly carries NO `lint-workflows` job (it cannot lint its own contract) — the exemption rides alongside the self-test one. The committed `pyproject.toml` version is permanently the `0.0.0.dev0` sentinel. Bumping a consumer means changing the SHA in its `.github/actions/setup-release-devkit/action.yml` wrapper; the pinned SHA must exist on the remote before consumer CI runs, so this repo's branch is always pushed first.

## Commands

One console script per verb (`get-app-version`, `release`, `prerelease`, `validate-release-plan`, `create-release`, `lint-workflows`, `merge-gate`, `update-pr-draft-release`; the workflow contract: script names and flags are the public API). Workflow jobs run them via `uv run --project "$RUNNER_TEMP/release-devkit" --locked --no-dev <verb>`; humans can run `uv run <verb>` from a checkout. Config defaults to `release-devkit.yaml` where optional.

| Command | Role |
|---|---|
| `get-app-version` | Print the version a CI build of an app should stamp: `{next_version}+{run}` — `next_version` derived from the app's declared `major_minor` and the `{name}-v*` version tags (prerelease-suffixed tags excluded; no in-line tag → `{major_minor}.0`), the same `next_version` `release` uses to tag the release so the build-time stamp matches the eventual release tag. Run number from `--run-number` or the ambient CI run number. The build-time half of the versioning boundary: this tool owns version derivation, build tools own stamping, and the consumer's workflow bridges the two — the emitted string is opaque to the build door that receives it. |
| `release` | Compute the publish plan from the version tags + path-diff, publish every changed package to its registries, bump and tag app versions, push per-package tags, then cut the GitHub Release (`create-release` runs internally whenever something published — there is no `published` output and no separate gated step), then reset the `dev-builds` draft (the dev pile is cleared once promoted to a CalVer release, so the next merge to dev starts a fresh pile). Naming law: `release` names the stable-channel event and its artifacts (plan, PR, GitHub Release); `prerelease` names the dev-channel event — parallel names for parallel channels. |
| `prerelease` | Dev-channel mode: publish immutable `-dev.<run-id>` prereleases of every path-diff-changed package to its registries, then append a per-run section to the `dev-builds` draft with the changed kinds' rows — packages (dev version + registry link) and apps (asset download links). App change detection is purely source-based — an app's APK is surfaced only when the app's source changed since its last version tag; package-driven app version bumps do NOT surface a duplicate APK, because the app source is unchanged and the build is identical. `--run-id` defaults to the ambient CI run id; never creates git tags, never touches app versions. Prints "Nothing to publish" and returns when no package changed and no app source changed. Named for the dev-channel event, parallel to `release` naming the stable-channel event. |
| `validate-release-plan` | Run the shared plan core (`load_config` → `resolve_edges` → `compute_plan` → app-version math) and print the plan. No flags, no env, no writes — the plan-time gate every publishing repo's integrate runs as a parallel root beside lint-workflows and preflight; it also catches every plan-time validation (sentinel misuse, never-published siblings, cyclic edges) before any registry call. |
| `lint-workflows` | The install-and-invocation gate: actionlint (pinned, checksum-verified) over `.github/workflows/*.yml` plus pure-Python signature validation of consumer checkouts, the one-step `setup-release-devkit` wrapper, the canonical run-step verb invocations (per-verb flags and env included, each a single physical line in the raw YAML — folded `>-` blocks hide from the parsed regexes, so devkit verbs never fold; non-verb `run:` steps longer than 120 characters may fold, uniformly indented, and the lint validates the joined command), the canonical setup-uv placement (every verb job spells it before the wrapper; exactly one cache-writing setup-uv per integrate.yml — in `preflight` where a battery survives, in `lint-workflows` where that job is the repo's only verification job), the `lint-workflows`-job-required rule with the integrate needs wiring, the release-workflow name/concurrency spelling, the validate-release-plan-job-required-iff-publishing rule, and the NuGet-login-mint-iff-nuget-config rule with the no-`environment:`-key scrub. Runs as its own parallel-root job in every consumer's integrate (release-devkit's own `integrate.yml` is the one exemption, riding the self-test one). |
| `create-release` | Assemble release notes (package versions with registry links, app versions), pull each app's build artifacts from its builds shelf (`pull_build` at the matched CI run) and cut the CalVer-named (`YYYY.MM.N`, counting releases within the month) GitHub Release with those assets. `release` calls it internally on every real publish; as a standalone verb it exists for manual re-creates. Registry login for the ORAS pulls is derived, never env-plumbed: the verb reads ambient `GITHUB_TOKEN` + `GITHUB_ACTOR` and passes them through `pull_build`'s explicit-parameter door into ci-devkit's `ensure_registry_login`. |
| `merge-gate` | The bors-model lander, woken two ways (the `ready-to-merge` label event and Integrate's green completion — both wakes pass the same `HEAD_SHA: ${{ github.event.pull_request.head.sha || github.event.workflow_run.head_sha }}`, the `||` dispatch idiom of the merge-bot checkout ref): resolve the open PR to `dev` whose head is that SHA, refuse unless the PR is OPEN and carries the `ready-to-merge` label (the workflow_run payload carries neither fact, so the verb asserts both on every wake), assert ALL check-runs green on the PR head SHA (the whole battery minus the gate's own check name — a red `merge-gate` run is the lander refusing, never a verification failure, so a stale workflow_run wake on an old pin cannot deadlock the labeled wake; per-repo batteries differ; the rollup is read via `gh pr view --json statusCheckRollup`, whose CheckRun entries carry `status` + `conclusion` and no `state` key — green is `COMPLETED` with conclusion `SUCCESS` or `SKIPPED`; if every blocking entry is still pending, print a waiting line and exit 0 — the other wake will land it, and a red run for label-early is noise; any terminal failure refuses loudly with PR number + head SHA), refuse unless the checkout HEAD is the PR head and `dev` is an ancestor of it (semi-linear merge), checkout `dev`, merge the PR head with `--no-ff`, and push the merge commit to `dev` with git credentials minted from the merge-bot App installation token (never `github.token` — the job token cannot bypass the ruleset), then delete the merged PR's head branch (guarding against `dev`/`main`, tolerating already-deleted branches via `ls-remote --heads` existence check), then delete the `pr-{N}` draft release (tolerating absence — a PR without builds never created one). The draft deletion rides the minted App token, which must carry `Contents: write` to delete releases via the API; if the App lacks that permission the `gh release delete` fails loudly. Abandoned PRs (closed without merge) never trigger `merge-gate`, so their `pr-{N}` drafts linger — they are `draft: true` (hidden), a minor accepted leak. |
| `update-pr-draft-release` | Pull each app's build artifacts from the ghcr builds shelf at the CI run number (`--run-number`), upload them as `{stem}-run-{N}.{ext}` assets to a `pr-{N}` draft GitHub Release (created if absent, `--clobber` overwrites same-named assets so re-runs replace while new runs append), and emit each asset's `browser_download_url` to `$GITHUB_STEP_SUMMARY`. The PR-scoped draft surface: one draft per open PR, accumulating every CI run's build. No-op when no app declares `builds`. Flags `--pr-number <N>` `--run-number <M>`. |

Verbs have no composite actions — they are plain run steps in the caller's workflow, invoked as `uv run --project "$RUNNER_TEMP/release-devkit" --locked --no-dev <verb>` after the `setup-release-devkit` wrapper has installed the tool. The workflow verbs: `get-app-version`, `release`, `prerelease`, `validate-release-plan`, `lint-workflows`, `merge-gate`, `update-pr-draft-release` (`create-release` stays a manual CLI verb — it always runs inside `release`, so no workflow calls it directly). The invocation grammar is fixed and `lint-workflows`-enforced: `get-app-version` takes `--app <name>`; `update-pr-draft-release` takes `--pr-number <N> --run-number <M>`; all others take no flags; `release`, `prerelease`, and `update-pr-draft-release` require env `GITHUB_TOKEN: ${{ github.token }}`, spelled in the step; `validate-release-plan` carries no env of the tool's; nuget repos add the canonical `NuGet/login@v1` mint step (`id: nuget-login`, `user` from the `NUGET_USER` org secret) between the wrapper and the verb, and the prerelease/release verb steps spell `NUGET_API_KEY: ${{ steps.nuget-login.outputs.NUGET_API_KEY }}` — all three registries are keyless from the consumer's secret store; `merge-gate` requires env `GITHUB_TOKEN: ${{ steps.mint.outputs.token }}` + `HEAD_SHA: ${{ github.event.pull_request.head.sha || github.event.workflow_run.head_sha }}` (populated on both wakes by the same `||` dispatch) and a canonical `actions/create-github-app-token@v3` mint step (`id: mint`, app-id from the `MERGE_BOT_APP_ID` org variable, private-key from the `MERGE_BOT_APP_PRIVATE_KEY` org secret) between the wrapper and the verb. The action's current line deprecates `app-id` in favor of `client-id`, but the pinned actionlint's bundled metadata predates that flip and rejects the `client-id` spelling — the canonical contract stays `app-id` until the actionlint pin bumps past the metadata change. There is no `CI_REGISTRY_*` anywhere in this tool's contract: release-devkit is explicitly GitHub-coupled and derives every registry login from `GITHUB_TOKEN` + ambient `GITHUB_ACTOR` through ci-devkit's explicit-parameter door (`CI_REGISTRY_*` survives only in the unity cache/license jobs, whose consumer is the neutral floor itself). App handling in `release` is unconditional: app versions bump whenever any package publishes, because a filtered run that skipped them would permanently lose the app-bump window (nothing later re-triggers it — the app's own path is unchanged and no package publishes again).

## Consumption shape

Every publishing consumer runs three workflow files, split by triggering event (non-publishing repos — the infra trio — run `integrate.yml` + `merge-gate.yml` only): `integrate.yml` — `on: pull_request: [dev]` + `workflow_dispatch`, the verify battery, `concurrency: group: integrate-${{ github.ref }}, cancel-in-progress: true`; `release.yml` (workflow name `Release`) — `on: push: [main, dev]`, the delivery jobs gated by branch, `concurrency: group: release-${{ github.ref }}` with NO cancel (queue is the policy: the `main` group is the release mutex that must never drop a release mid-flight, and queuing dev publishes guarantees every merge to dev gets its prerelease set 1:1 — a cancelled mid-publish run would leave that merge's prereleases partial); the file stays ONE file for both channels: npm allows one trusted publisher per package, bound to a single workflow filename — a split would leave one channel unpublishable; and `merge-gate.yml` — dual-triggered: `on: pull_request` to `dev`, `types: [labeled]` (the consent wake — the label is `ready-to-merge`, standing intent, not a fire-now command) plus `on: workflow_run: workflows: [Integrate], types: [completed]` (the readiness wake), every job gated on the combined `if:` (`github.event.label.name == 'ready-to-merge' || (github.event_name == 'workflow_run' && github.event.workflow_run.conclusion == 'success')`), and the per-PR concurrency group `merge-gate-${{ github.event.pull_request.number || github.event.workflow_run.head_branch }}` with NO cancel-in-progress — serialization gives every wake a complete execution and the verb is idempotent (the `||` fallback is load-bearing: under workflow_run events `github.event.pull_request` does not exist, and a bare key would globally serialize all PRs' gates). The `workflow_run` use is a scoped carve-out of the org-wide ban — sanctioned ONLY as merge-gate's completion wake, still forbidden as a delivery bridge; it exists because no `pull_request` activity type fires at checks-green and `check_run`/`check_suite` never fire for Actions-created checks, and its payload carries no PR number and no labels, which is why the verb-side label assert is mandatory and the head-SHA wake re-resolves the PR. The workflow_run receiver is read from the DEFAULT branch (`main`): the green wake is inert per repo until `merge-gate.yml` reaches `main` via that repo's next release, while the label wake works from `dev` immediately — harmless, because the file is a thin shell (all policy rides the verb, invoked from the PR-head checkout), so main's copy going stale costs nothing. All of this is lint-enforced byte-exact. Still never `pull_request: [main]`: promotion is a push (`git push origin <sha>:main`), so no PR to `main` exists to fire anything; `main`'s branch protection must require no status checks.

Jobs never `needs` across the file boundary — verification certifies on PRs, delivery runs on the landing push; a push run re-verifying would be double-running. Inside `integrate.yml`, `lint-workflows`, `validate-release-plan`, and `mirror-images` (where present) are the parallel roots of the verify DAG (mirroring is a near-always no-op, and when `preflight` itself consumes mirror-prefixed images the inversion is forced anyway). `preflight` — where a real battery survives — `needs: [lint-workflows]` (plus `mirror-images` where present), so contract breaks kill the battery early through the transitive needs; where the entire preflight was the lint step, the preflight job dissolves and `lint-workflows` (carrying the saver setup-uv) is the repo's verification root. Matrix getters keep `needs: [preflight, validate-release-plan]` (or `[lint-workflows, validate-release-plan]` where preflight dissolved): expensive legs die early on contract breaks via the transitive needs — a broken `release-devkit.yaml` fails `validate-release-plan` at minute 1 instead of after a 40-minute build that could never ship. The delivery jobs in `release.yml` stand alone.

Every verb-owning job prepares in this order: the consumer checkout, then `astral-sh/setup-uv@v7`, then the `setup-release-devkit` wrapper step, then the verb run steps — enforced convention: every consumer's jobs read identically, the verb steps always find both the consumer tree and the installed tool, and the sanctioned steps between wrapper and verb are exactly the token mints: the merge-gate job's `create-github-app-token` and the nuget delivery jobs' `NuGet/login@v1`. The setup-uv spellings are canonical: every job but the cache writer uses the restore form (`enable-cache: true`, `save-cache: "false"`), and the ONE cache writer (`save-cache: "true"` — exactly one per integrate.yml, so parallel jobs never race cache saves) lives in `preflight` where a battery survives, in `lint-workflows` where that job is the repo's only verification job. The checkout shapes are four lint-enforced signatures. The ref law is file-relative: `integrate.yml` checkouts spell `ref: ${{ github.event.pull_request.head.sha }}` — the exact certified head, GitHub's documented head-checkout form (certifying the head, not the synthetic PR merge commit, is deliberate: the certified tree is the landed tree byte-for-byte; on `workflow_dispatch` the expression is empty and checkout falls back to the event default, the dispatched commit). `release.yml` checkouts spell NO ref — the push event's default checkout is already the exact pushed commit, and a spelled branch-name ref is a movable pointer that can race a queued delivery run's newer push (two bot merges queue two Release runs; a branch-named checkout in the first could grab the second's tip and publish the wrong tree). One sentence per file: Integrate checks out the PR head, Release checks out what was pushed, merge-gate checks out the certified SHA.

- `checkout` — integrate: the head-SHA ref, default shallow depth; release: no ref (the event default). Always `persist-credentials: false`. Reads only the working tree: lint-workflows, preflight, mirror, matrix, builds.
- `checkout-with-tags` — the same ref law, `fetch-depth: 0`, `fetch-tags: true`, `persist-credentials: false`. Version math reads the tags and diffs against them: `validate-release-plan` (incl. `get-app-version`), `prerelease`.
- `checkout-with-tags-push` — the same ref law, `fetch-depth: 0`, `fetch-tags: true`, `persist-credentials: true` (spelled explicitly; this job's verb pushes the version tags it creates): `release` only.
- `merge-bot` — `ref: ${{ github.event.pull_request.head.sha || github.event.workflow_run.head_sha }}`, `fetch-depth: 0`, `persist-credentials: false` (workflow_run events carry no branch identity; the verb asserts checkout-is-head): `merge-gate` only.

Comments in the canonical files are minimal and end without a period: `# Perform a full clone, required for tags` above `fetch-depth: 0` in the tag checkouts, `# Persist credentials so that the release command can push release tags` above the release job's `persist-credentials: true`, and `# Perform a full clone, required so merge-gate can validate that this PR is a semi-linear merge into dev` above the gate's `fetch-depth: 0`. No checkout carries a comment on its `ref:` — the integrate head-SHA literal, the release no-ref default, and the merge-bot dual-payload ref all read from context — and none on `fetch-tags` or `persist-credentials: false`. A documented convention, not lint-enforced. Repeated steps within a file use whole-step YAML anchors (`- &checkout`, `- &checkout-with-tags`, `- &uv-restore`, `- &setup-release-devkit`, plus per-file extras like the unity env block and `Wipe workspace`), anchored at first use, no free-floating definitions, no merge keys (`<<:`), no cross-file aliasing. Step `name:` survives only when it says something the command does not (e.g. `Wipe workspace`); verb restatements (`name: lint-workflows` over `run: … lint-workflows`) die. Every `run:` step in the three canonical files is a single physical line — one space before the verb, flags on the same line — with one exception: a command longer than 120 characters may be a folded `>-` scalar with uniformly indented, non-blank continuations (the lint raw-joins the block and validates it — blank lines and uneven indents inside the fold are rejected, because fold semantics would silently turn them into newlines). Devkit verb invocations never fold: they stay raw so the canonical-spelling regexes see them (a fold puts the verb and its first flag on different lines with no visible space; the parse-time fold hides it, so lint checks the RAW text). The `lint-workflows` verb enforces all of this mechanically except the comments and names: checkout-signature matching, one-step wrapper validation, canonical invocation spellings with per-verb flags and env, the single-physical-line run-step rule, the verb-to-signature mapping, dead old-model `uses:` rejection, checkout- and setup-uv-before-wrapper-before-verb ordering, canonical setup-uv placement with the one-writer placement rule, the lint-workflows job extraction with the integrate needs wiring, the validate-release-plan-job-iff-publishing rule, the release workflow name/concurrency spelling, the merge-gate dual-trigger + concurrency + job-gate contract, the merge-bot-signature-and-mint-step contract, the `NuGet/login@v1`-mint-iff-nuget-config rule with the minted `NUGET_API_KEY` verb-env source, the no-`environment:`-key rule, and the `checkout-with-tags-push`-only-in-release rule.

- `lint-workflows` (every repo, in `integrate.yml`, parallel root) — checkout + restore setup-uv + wrapper + the `lint-workflows` run step (the saver form where it is the repo's only verification job). release-devkit's own `integrate.yml` is the one exemption.
- `preflight` (repos with a real battery, in `integrate.yml`) — checkout + the saver setup-uv + the repo's battery, `needs: [lint-workflows]` (plus `mirror-images` where present). Never carries tokens.
- `validate-release-plan` (publishing repos, in `integrate.yml`, parallel root) — checkout-with-tags + restore setup-uv + wrapper + `get-app-version --app <name>` (app repos; version exported as the job output consumers read as `needs.validate-release-plan.outputs.version`) + the `validate-release-plan` run step. `permissions: contents: read`, no environment, no env vars.
- `prerelease` (in `release.yml`, `dev` gate) — checkout-with-tags + restore setup-uv + wrapper + (nuget repos: the `NuGet/login@v1` mint step) + the `prerelease` run step (env `GITHUB_TOKEN`) with no `--run-id` (the ambient CI run id is the correct number). No tags, no releases of its own; appends a per-run section to the `dev-builds` draft with changed kinds' rows (packages: dev version + registry link; apps: asset download links). Permissions `contents: write` + `packages: read` + `actions: read` (for `matched_ci_run_number`) in addition to the existing `id-token: write` (trusted publishing). No-op when no package changed and no app source changed.
- `release` (in `release.yml`, `main` gate) — checkout-with-tags-push + restore setup-uv + wrapper + (nuget repos: the `NuGet/login@v1` mint step) + the `release` run step (env `GITHUB_TOKEN`). The dev draft reset runs inside the verb after the CalVer release is cut — no separate reset step. Permissions `contents: write` + `id-token: write` (+ `packages: write`, `actions: read` where apps pull the builds shelf or the matched-CI-run lookup queries the Actions API). No `environment:` key — delivery is gated by the branch, not an environment. The GitHub Release is cut inside the command — no separate `create-release` step.
- `merge-gate` (in `merge-gate.yml`, dual wake) — merge-bot checkout + restore setup-uv + wrapper + the `actions/create-github-app-token@v3` mint step + the `merge-gate` run step. The job carries only `permissions: contents: read` (the checkout); every write path — check-run reads, the dev push, the PR draft deletion — rides the minted App token, which the ruleset's Integration bypass is keyed to. The App must additionally carry `Contents: write` to delete the `pr-{N}` draft release via the API.
- `update-pr-draft-release` (in `integrate.yml`, PR event, `if: github.event.pull_request`, `needs: [build-unity]`) — checkout + restore setup-uv + wrapper + the `update-pr-draft-release` run step (`--pr-number ${{ github.event.pull_request.number }} --run-number ${{ github.run_number }}`, env `GITHUB_TOKEN`). Permissions `contents: write` + `packages: read`. Runs once after all matrix legs, iterating all `apps[].builds.artifacts` in one job. No-op when no app declares `builds`.

## Landing changes (the bors model)

`dev` is evergreen: nothing lands on it that was not certified green at the exact SHA that lands. The door is a PR — push a branch, open a PR to `dev`, let `integrate.yml` certify the head, then apply the `ready-to-merge` label (adjective, standing intent: it means "land this when green", survives rebases and further pushes, and never needs re-applying). Two wakes run the `merge-gate` verb — the label event (consent) and Integrate's green completion (readiness); the verb owns all policy on every wake: label present, state OPEN, checkout-is-head, all-green, rebased-onto-dev. This deletes wait-for-green (no in-job polling, no runner occupancy, no timeout knob) and the human re-label loop in every ordering — label-early, rebase, or green-first all converge. The verb merges the PR into `dev` with `--no-ff` (semi-linear: the PR is already rebased onto `dev`, so the merge commit marks the merge point without changing the tree), deletes the merged PR's head branch (guarding against `dev`/`main`, tolerating already-deleted branches), deletes the merged PR's `pr-{N}` draft release, and the landing push fires `release.yml` (the delivery half). The merge bot holds the `evergreen-dev` ruleset's Integration bypass (managed in infra-github-org); with the ruleset active it is the only door — a merge commit marks the point, no squash rewrites, the certified head's tree is the landed tree. Never label a PR in a repo without a live verification job: the all-green assert is vacuously true on zero checks, and a lint-less repo would merge uncertified.

## The CI-commit-free invariants

CI and release workflows must not create non-merge commits on any branch — the merge-bot's `--no-ff` merge commit on `dev` is the only commit CI creates, and `dev` → `main` merges are always true fast-forwards. The machinery that makes that possible lives here:

- **Version tracking**: per-package git tags (`{name}-v{semver}`, e.g. `placeframe-api-client-v0.1.8`, `capture-tool-v0.2.0`), never committed state files. The git-tag primitives (`list_tag_versions`, `has_changes_since_tag`, `create_and_push_tag`) live in `tags.py` here — version-tags semantics are this repo's concern; ci-devkit is the GHA runner floor.
- **Change detection**: `git diff --quiet <last-tag> HEAD -- <path>`, never content hashing. No cascade: an unchanged dependent is an immutable, coherent pairing — consumers adopt newer siblings through their own pins (UPM/npm treat declared dependency values as minimums, so a newer sibling always satisfies).
- **Version scheme**: the major.minor is config data, the patch is tag data. Every package and app entry declares a required `major_minor` string (`"M.m"`); the planned version is the highest stable tag within that line plus one patch, or `.0` when the line has no tags — a first release is whatever the declared line says. A declared line below any existing tagged version fails loudly (never compute downward). Per-package numbers are independent within one release event — no lockstep.
- **Manifest version sentinels**: Unity `package.json` versions are permanently `0.0.0+local` in the repo; patched ephemerally during `npm publish` and restored immediately — never committed. Python `pyproject.toml` versions are permanently `0.0.0.dev0` in the repo; patched ephemerally around `uv build` and restored immediately. The sdist/wheel carries the real version; the committed file never does.

## The dependency-edge law

Same-release-unit dependency edges are **inferred from manifests**, not authored in config: each package's manifest dependencies (package.json `dependencies` for npm, `[project].dependencies` for pypi, csproj `PackageReference` for nuget) are intersected with the config's registry identities; a match is an edge, everything else is an external dependency that ships verbatim. Edges drive topological plan ordering — dependencies-first, load-bearing for nuget, where `dotnet pack` restores the sibling from the registry — and validation only, never version selection.

Same-unit dependencies are authored as the sentinel `0.0.0+local` — one string that is valid semver (build metadata), PEP 440 (local version), and NuGet. The concrete version exists only in the published artifact, injected at publish from the event's plan: the sibling's new version if it co-publishes, its current tag if unchanged (HEAD is then byte-identical to that release), and a loud error if it never published. The dev channel injects a co-publishing sibling's `-dev.<run-id>` spelling and an unchanged sibling's current stable tag. Cross-unit and ecosystem dependencies are authored exact and shipped verbatim — adoption is a human commit.

Plan-time validations, all atomic before any registry call, all caught by `validate-release-plan`: a sentinel on a non-config identity; a real version where a config identity expects the sentinel (hard flip — staleness cannot ship); a sibling that has never published; cyclic edges.

### Reference regimes (how same-unit dependencies are wired on disk)

| Regime | Local | Publish |
|---|---|
| Unity sibling, same project | asmdef assembly-name references | package.json sentinel, ephemeral patch |
| Same repo, outside the consuming project | `file:` path in the project's Packages/manifest.json + asmdef name | package.json sentinel, ephemeral patch |
| Cross-repo (lbe-toolkit → placeframe) | exact registry pin in the consumer's project manifest | the same adopted pin, verbatim |
| Ecosystem deps (UniTask, org.nuget.*) | authored exact | verbatim |
| nuget sibling | ProjectReference (version-free) | `PackageReference Version="$(Prop)"` with the property defaulting to `0.0.0+local`; injected via `-p:<Prop>=<version>` beside `-p:Version` |
| pypi sibling | `[tool.uv.sources]` workspace override | `name==0.0.0+local`, specifier patched ephemerally |

## Release units

The repo is the release unit: repos release independently; one release event publishes every changed package in the repo together; a package unchanged since its last tag is skipped (registries are immutable — there is nothing to publish), and dependents are never republished for a sibling's change.

## Dev channel

`prerelease` publishes immutable prereleases of every path-diff-changed package and appends a per-run section to the `dev-builds` draft with the changed kinds' rows (packages: dev version + registry link; apps: asset download links); it creates no git tags, bumps no app versions, and opens no release (the dev draft is a `draft: true` GitHub Release, not a published release). Versions are keyed by the CI run id and spelled per registry — `{base}-dev.{run_id}` where semver allows it (nuget, npm), `{base}.dev{run_id}` on PyPI — because no single string is both valid semver and valid PEP 440. The base is the next version derived from the declared `major_minor` and the version tags, so a package's dev versions share one base until the stable flow tags it. npm prereleases ride the single inert `dev` dist-tag so `latest` never moves. The job prints the exact published versions; that print is the consumption interface — consumers pin by hand, there is no discovery tooling.

## Draft release surfaces

Three surfaces expose CI-built APKs as downloadable links, all mirroring the ghcr builds shelf (which stays canonical — `ci-build-unity` pushes `run-{N}` tags there, `install` pulls from there, `create-release` staples from there on main):

- **PR draft** (`pr-{N}` tag): one draft release per open PR. Each CI run appends a run-suffixed asset — all builds visible, not just latest. `update-pr-draft-release` runs in `integrate.yml`; `merge-gate` deletes the draft after the merge. Drafts are `draft: true` — hidden from the published Releases page.
- **Dev draft** (`dev-builds` tag): one rolling draft accumulating every merged PR's section since the last promotion to main. `prerelease` appends a per-run section in `release.yml` dev-push (packages: dev version + registry link; apps: asset download links); `release` resets the draft after cutting the CalVer release. The tag is `dev-builds` (not `dev`, which collides with the `dev` branch in the refs namespace).
- **Main release** (CalVer `YYYY.MM.N`): unchanged — `create-release` cuts one asset per platform (the promoted build).

Asset naming: drafts use `{stem}-run-{N}.{ext}` where stem = the configured `name` without extension (or the source file's stem when `name` is unset); the main CalVer release keeps the bare configured `name`. `--clobber` on upload overwrites same-named assets (re-run safety) and appends uniquely-named ones (new-run append). `pull_build_assets` (shared between `create-release`, `prerelease`, and `update-pr-draft-release`) pulls from the shelf and stages files; each caller owns the final naming.

Dev draft section mechanics: each section is keyed by an `<a id="run-{N}"></a>` HTML anchor (release bodies get no auto heading anchors — inline HTML anchors render and `#anchor` fragments scroll to them). `append_draft_section` (`draft_releases.py`) does idempotent replace-or-append — same run number overwrites, new run number prepends (newest-first). The writing run's `$GITHUB_STEP_SUMMARY` links back to the draft's `untagged-<hash>` URL `#run-{N}` (draft tag-URLs 404 — `untagged-<hash>` from `gh release view --json url`). `release.yml`'s `release-${{ github.ref }}` no-cancel queue serializes dev prerelease runs, making the read-modify-write append safe.

## The Registry seam

`registries.Registry` is the registry adapter protocol (`publish(request: PublishRequest)`); `NuGetRegistry`, `NpmRegistry`, and `PyPIRegistry` implement it. A registry's identity (nuget package id, npm name, PyPI distribution name) is config data, not code — the same package can publish to several registries at one version. Config-declared registry names are validated against `registries.KNOWN_REGISTRIES` at load time.

`PyPIRegistry` shells out to `uv build` + `uv publish` and authenticates via trusted publishing (OIDC): it takes no credential, so the consuming workflow needs `id-token: write` and the PyPI project needs a configured (or pending) publisher for that repo/workflow. Idempotent re-publishing is handled by `uv publish --check-url` against the simple index. npm authenticates the same way — trusted publishing via `--provenance`, no token plumbing — and npm allows one trusted publisher per package, bound to a single workflow filename: every workflow that publishes a given package to npm must be the same file. nuget joins them through the official `NuGet/login@v1` action: it exchanges the job's OIDC token (audience `https://www.nuget.org`) with nuget.org's token endpoint (`POST /api/v2/token`, body `{username, tokenType: "ApiKey"}` — the username is the `NUGET_USER` org secret, a public profile name and routing parameter, not a credential) for a ~1h API key it `setSecret`-masks and exports as `NUGET_API_KEY`; the adapter consumes that minted key through the same `NUGET_API_KEY` env, so the consumer's secret store holds no nuget credential. nuget.org's trusted-publishing policy binds owner/repo + workflow filename, so `release.yml` must never be renamed — already npm law, now nuget law too.

## Config

`config.PublishConfig` (pydantic, loaded by `load_config`) validates the consumer's root `release-devkit.yaml`. The config-file law org-wide (home: this file; siblings reference it, they don't duplicate it): config lives beside the unit whose facts it carries; consumption model and config location are independent axes. A tool whose subject is the Python project configures from pyproject `[tool.<devkit>.*]` tables (the black/ruff pattern); every other devkit configures via one root `<devkit>.yaml` per repo. python-devkit is the one pyproject-table devkit (its subject is the Python workspace); unity-devkit is the one JSON exception (its config is read by C# inside Unity, which ships no YAML parser). release-devkit / openapi-client-codegen / docker-devkit are root `.yaml`. Strict loading: strictyaml rejects duplicate keys and preserves all scalars as strings (no implicit typing — unquoted `0.1` stays `"0.1"`); pydantic coerces per-field from the string-preserving parse with `extra="forbid"` on every model.

- The registry-mapping key is `registries`. Hard flip, no accept-both: unknown keys are rejected (`extra="forbid"`), so an unmigrated config fails loudly at load instead of silently publishing with zero registries.
- `ci_workflow` is required: it is the matched-CI-run lookup key (`gh api …/workflows/{name}/runs?head_sha=…`) that disambiguates whose build artifacts a release staples — several workflows run on the release SHA, including Release itself, so a `"ci.yml"` default would be silently wrong for repos whose CI file is named differently. The value names the builds-bearing workflow: post-split that is `integrate.yml` — the PR runs carry the build legs, and Release never builds. The lookup resolves the certified SHA that ran integrate — a merge commit (the semi-linear merge the merge-bot creates on `dev`) resolves its second parent (`parents[1] // self`, the PR head that ran integrate), a non-merge SHA resolves to itself — and yields that run's **run number**, which is the `run-{N}` tag every builds shelf carries. A SHA that reached `dev` without an integrate run fails the lookup loudly ("cannot release untested code") — that is the design: only PR-certified SHAs are releasable.
- An app entry may declare a `builds` shelf: `registry` (the builds namespace, e.g. `ghcr.io/{owner}/{repo}/builds`) plus an `artifacts` list whose entries carry `project` and `platform` — composed through ci-devkit's `build_reference`, so the pull side cannot drift from whatever pushed the shelf. `project`/`platform` must be the push side's exact spelling (the Unity project name and platform for APKs; docker-devkit's lock convention for image locks), never the app/tag-prefix name. Optional `file` selects which pulled layer becomes the asset when a build pushes several (APK builds also push `BuildReport.json`); optional `name` renames the asset on the release (e.g. `CaptureTool-AndroidMobile.apk`). Apps without a `builds` section release with no stapled build assets.
- The mapping fields (`packages`, `apps`) may be omitted when empty — an apps-only repo declares no `packages` key at all. Both key packages and apps by name, which doubles as the git-tag prefix (`{name}-v{semver}`); apps carry no separate `display_name` or `tag_prefix`. There is no `requires` field and no config-level version check: the wrapper action's SHA pin is the only version control, and a config cannot meaningfully constrain a tool whose version is a commit hash.
